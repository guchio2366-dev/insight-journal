ラベル要素は使い回し、地図移動に応じた座標更新を1描画フレームにまとめる。全都市分の要素を毎回作り直さない。既存の都市選択リストも、キーボード操作と代替表示の補助として残す。

### 4.2 都市を基準にした雨温図

iPad・PCでは都市点の上下左右を候補にし、都市との距離を優先して1枚の雨温図を置く。点・都市名とカードの間隔は12〜24 CSS pxを目安とし、端でずらす場合は短い引出線で対応を示す。地図の反対側の空き領域へ配置する現行方式は自然環境の雨温図には使わない。

iPhoneでは幅約200〜240 CSS pxの小型雨温図を都市近くに置く。都市名、12か月の棒と折れ線、単位、目盛りを保持する。「大きく見る」で地図直下に詳細図・月別数値・観測所情報を開ける。小型図と詳細図は同じ都市データ・目盛りを使う。

全国表示の12都市名、選択都市の点・名前、地図操作、表示切替をカードで隠さない。まずラベルとカードを一緒に再配置し、次に小型図を使う。小型図だけでも成立しない画面では、都市近接という要件を無断で地図下のみの表示へ変更せず、実装時に配置案を確認する。文字を極端に小さくして収めない。

パンで選択都市が画面外になったら地図内カードを隠し、都市の選択は保持する。選択リスト付近に都市名と「都市へ戻る」を残し、この操作を押した時だけ地図を移動する。再び画面内に入れば近接表示を復元する。

雨温図は既存の月別NOAA平年値を使用し、降水量0〜350mm、気温−10〜40℃の共通目盛りを維持する。小型図でも12か月を保持し、都市ごとの自動伸縮をしない。縦軸の上下位置が降水量と気温の直接的な大小比較を意味しないよう、両軸の単位を明記する。

## 5. 気候面の選択（R03）

タップした地点について、表示に使用する分類ID格子を参照する。雨温図の都市地点判定と同じ分類体系を使い、画像の見た目のRGBから分類を推測しない。

| 先頭コード | 大きな見出し |
|---|---|
| A | 熱帯 |
| B | 乾燥帯 |
| C | 温帯 |
| D | 冷帯（亜寒帯） |
| E | 寒帯 |

カードは「大区分 → 個別の日本語分類名・コード → 1〜3文の特徴 → 出典・期間」の順とする。例えばCsaであれば、温帯を見出しにして地中海性気候とCsaを併記する。具体的な分類名は既存凡例の語彙に合わせる。

分類未収録・海域・対象外は分類しない。ワシントンD.C.の観測地点にある欠測は、近くの格子から補完せず既存注記を維持する。都市ラベルを押したイベントを気候面へ伝播させて、雨温図が直後に地域カードへ上書きされることを防ぐ。

既存の気候画像と分類ID画像の投影・範囲を共通化する。代替画像でも画像の余白を除いた描画矩形から地理座標へ変換し、同じID格子を参照する。海岸・格子境界の数地点でWebGL表示と判定を比較する。画像の拡大縮小でカテゴリIDを補間しない。

## 6. 年降水量の等値線（R04）

### 6.1 表示と教育上の意味

水資源に年降水量500mm・1,000mmの線を追加する。薄い紫の破線と「年降水量 1,000mm」等の線上ラベルで、河川の青い実線、帯水層の斜線、標高の茶色線と区別する。線を切って河川・地下水だけを見る操作も用意する。

1,500mm・2,000mmは追加候補とする。全国表示で線が混雑する場合や容量上限に近づく場合は省き、その採否を実装記録に残す。基本の500mm・1,000mmを省く場合は利用者に確認する。

凡例には「年降水量／1991〜2020年平均／全国比較用」と記す。1,000mmを「小麦が生産可能になる境界」とは表示しない。小麦の生育には生育期の水分、気温、土壌、灌漑などが関わり、年降水量だけで可否を判定できない。FAOが示す小麦などの450〜650mmという目安は生育期間の作物水需要であり、年間降水量の栽培境界ではない。[FAOの作物水需要](https://www.fao.org/4/s2022e/s2022e02.htm)

地図の線は水分条件を比較する補助として使う。小麦産地との対応は農業タブへ同じ位置で移動して確認する。西経100度の直線を実際の等降水量線の代用にしない。

### 6.2 データと処理

候補はPRISMの米国本土1991〜2020年の年降水量平年値・4km格子である。NOAA都市雨温図と期間はそろえるが、PRISMは面の推定値、雨温図は観測所の平年値という違いを出典欄で説明する。両者が同じ値になることを保証しない。[PRISM平年値](https://prism.oregonstate.edu/normals/)

実装時は年間格子1種類を取得し、投影された距離座標で等値線を生成・簡略化してから配信用座標へ変換する。全国の月別・日別データは取得しない。12都市を補間して全国の線を作らない。初期の簡略化許容差は2kmを候補とし、4kmまでの調整は沿岸・山地・対象外マスクの確認後に判断する。

格子欠測部分を横切る線、海上への不正な接続、分断された線同士の結合を防ぐ。配信物には対象期間、元格子解像度、処理方法、簡略化許容差、単位、ハッシュを記録する。元格子より細かい精度があると説明しない。

ブラウザでは作成済みの全国GeoJSON gzipを一度読み、等値線の生成は行わない。選択は必須にせず、線上の数値と凡例で読めることを優先する。代替表示にも同じ線を重ねた画像を用意し、入／切に対応する。PRISMの再配布・引用条件を確認し、データ出典とアクセス日を掲載する。[PRISM利用条件](https://prism.oregonstate.edu/terms/)

## 7. 地形・土壌（R05）

### 7.1 分布データの採用条件

土壌は「地形・土壌」表示内の追加レイヤーとし、5番目の上位タブは増やさない。土壌を入れると地形陰影を弱めて分布色を見せ、山脈・平原の名前は残す。切ると現行の地形表示へ戻る。

USDA NRCSの全国を一般化した土壌分類図を第一候補とする。ただし本書作成時点で、採用可能なファイルURL、分類属性、容量、利用条件の照合は完了していない。大学の土壌解説ページを分布GISの出典として扱わない。次の条件を満たすデータを実装前に確定する。

- 米国本土を覆い、境界・分類コード・欠測を識別できる。
- 土壌分類体系と凡例が公開され、一般化の程度を説明できる。
- 再配布条件を確認でき、取得・加工を全国の詳細土壌データより小さく済ませられる。
- 表示する分布とタップ時の分類を同じデータから作れる。

gNATSGOやSSURGOの全国詳細データを先に大量取得してから縮小する方法は採らない。小さな公的分類図が得られない場合は、その機能のデータ作業を止め、確認済みの選択肢を提示する。実分布を代表地域の手描き図へ無断で置き換えない。

### 7.2 土壌の説明

高校地理で理解しやすい語彙を入口にし、原データの分類名・コードを併記する。教育用の土壌名とUSDA分類の間に一対一対応がない場合は、そのまま異なる体系として説明する。

| 説明の重点 | 原データで想定する分類 | 地域・特徴の扱い | 作物への言及 |
|---|---|---|---|
| 草原の暗色土・プレーリーの土壌 | Mollisols | 大平原・中西部など。厚い暗色の表層と有機物を説明 | トウモロコシ・大豆・小麦などとの地域的対応を確認して記載。水分条件を添える |
| 赤黄色の強く風化した土壌 | Ultisols | 南東部など。酸性・養分溶脱、管理の必要性を説明 | 実際の作物と石灰・施肥等の管理を出典付きで説明 |
| ポドゾル化した土壌 | Spodosols | 酸性・溶脱・集積を説明。冷涼地域だけに限定しない | 森林利用や栽培上の制約を優先し、無理に推奨作物を割り当てない |
| ラトソル等の熱帯の強風化土 | Oxisolsとの関係を説明 | 米国本土の主要分布として色を付けない | 用語の補足にとどめ、今回の対象範囲を広げない |

Mollisolsの全域をチェルノーゼムと呼ばない。「チェルノーゼム」「栗色土」「ラトソル」などを分布凡例へ採用するには、採用データまたは対応資料がその名称と境界を裏付ける必要がある。名称を見慣れたものにするためだけに、異なる分類を同一視しない。

分類体系に他の土壌が含まれる場合は、その分布を消さず凡例に残す。重点3分類以外を「土壌なし」と表示しない。データ未収録、海域、その他の分類を区別する。

土壌カードは「教育用の説明 → 原分類 → 主な分布 → 水・養分・酸性等の特徴 → 作物との関係と条件 → 出典」とする。土壌分類だけで作物適性を断定せず、気候、排水、土性、灌漑、管理条件を付記する。地下水の帯水層と表土の保水性も混同しない。

分類解説の参考：[Mollisols](https://www.uidaho.edu/agricultural-life-sciences/soil-orders/mollisols)、[Ultisols](https://www.uidaho.edu/agricultural-life-sciences/soil-orders/ultisols)、[Spodosols](https://www.uidaho.edu/agricultural-life-sciences/soil-orders/spodosols)、[Oxisols](https://www.uidaho.edu/agricultural-life-sciences/soil-orders/oxisols)。これらは土壌特性の根拠であり、個々の作物への適性評価や今回採用するGISを確定するものではない。

### 7.3 配信形式

基本案は、全国用の分類色PNGと分類ID PNGを同一範囲で作り、色の表示と地域タップを分ける方式とする。出力は最大1,600×970画素を目安にし、原データ以上の地理精度を示さない。分類IDは最近傍で扱い、色やコードを連続補間しない。

土壌を初めて入れた時だけ取得し、別の表示では読まない。分類IDは一度だけ8bit配列へ抽出し、一時RGBA画像やCanvasバッファを解放する。元の分類が8bitで表せない場合は分類対応表で配信用IDを明示的に割り当てる。

同じデータをより小さな一般化ポリゴンで配信できる場合は形式変更を裁量内とする。ただし同じ分布・分類・欠測を保ち、画面とタップ結果を一致させる。

## 8. 地形名の選択（R06）

初版で必須とする固有名詞は、ロッキー山脈、アパラチア山脈、カスケード山脈、シエラネバダ山脈、コロラド高原、グレートベースン、グレートプレーンズ、中央低地、大西洋岸平野の9件とする。既存の説明とIDを再利用する。

名前を押すと近くに短い説明カードを開く。本文は「どこにあるか」「高さ・地形の特徴」「気候・水資源・農業との関係」を対象に応じて2〜4文で示す。全国に同じ一般文を割り当てない。高さや成因を追加する場合は個別出典を確認する。

既存のエリア選択・一覧選択も残す。土壌を表示していても名前を押した時は地形説明を優先し、名前以外の土壌面を押した時は土壌カードを開く。操作可能な名前は見た目を統一し、説明のない名称をボタンにしない。

## 9. 標高の淡い色付け（R07）

保存済みUSGS 3DEP由来DEMを再利用し、全国用の標高色画像1枚を追加する。16個のTIFFは出典記録・範囲・ハッシュを照合し、順次縮小処理する。元DEMの全国再取得や詳細等高線の再生成を必要条件にしない。

低地の明るいクリーム色から、高地の淡い黄土色・茶色へ連続的に変える。色は標高に対応させ、陰影の明るさを標高として着色しない。地形表示の陰影と混同しないよう、濃い起伏表現を重ねない。

全国共通の0・500・1,000・2,000・3,000・4,000mを含む凡例を示し、0m未満と最高域の扱いも凡例または注記で明示する。海域と欠測は透明にし、負の標高を海域扱いしない。拡大や地域移動で色の目盛りを変えない。

画像は最大1,600×970画素を目安にし、全国線と同じ投影・範囲で配置する。圧縮や縮小後に山地・平原・海岸で位置ずれがないことを確認する。既存の500m間隔線、1,000mごとの主要線、標高ラベルを画像の前面に置く。

色は高さの概観、線は標高差を読むために使う。拡大しても線の間隔は500mのままである。低解像度画像から山頂の正確な高さを読み取れるとは説明しない。

### 10.1 開発・転送と、閲覧時の負荷を分ける

| 全国の等降水量線 | 年間格子1種類の取得と1回の加工 | 水資源を開いた時の小さな線データ1件 | 基本2本。余裕があれば追加2本 |
| 全国の土壌分類 | 出典・分類対応・境界確認が主な不確実要因 | 選択時の画像とID配列。地域別キャッシュ不要 | 入手条件を確認して実装 |

難所は、新しい等高線を多数転送することより、土壌の分類と分布を正しく対応させること、狭い画面で都市名と雨温図を同時に読める配置を作ることにある。所要時間は実装前の推定だけで断定せず、取得、加工、転送、検証、再試行を分けて記録する。

### 10.2 配信量の設計上限

以下は未計測の設計上限であり、達成済みの数値ではない。KB・MBは10進で数える。画像はファイルサイズ、gzipは圧縮済み実バイトで数え、HTTPヘッダーは除く。実測時にはサイト全体の転送量も別に記録する。

| 対象 | 上限 | 超過時の調整順 |
|---|---|---|
| 通常の気候初期表示のHTML・JS・CSS増分 | 圧縮後合計150KB | 共通化、不要コードを除く。新しい地図ライブラリを追加しない |
| 等降水量線・固有メタデータ | 圧縮合計400KB、展開JSON 2MB、座標数40,000以下 | 追加線を省く、検証可能な範囲で線を簡略化 |
| 土壌色・ID・凡例・固有メタデータ | ファイル合計800KB | 小さな全国分類図を使い、画素数・形式を調整 |
| 標高色画像・固有メタデータ | 合計350KB | 画像サイズ・圧縮を調整 |
| 新規・更新する代替画像の差分 | 正の増分合計450KB | 既存画像を更新・共用し、重複画像を避ける |
| 自然環境の公開データ増分 | 正の増分合計2.0MB | 上記の内訳を合計し、削除で別の肥大化を相殺しない |

上限どおりなら、既存11資産の3.25MBに対し同等の集計範囲は約5.25MB以内となる。これは4表示を全て使用した場合に関係する配信資産の総量であり、初回通信量の約束ではない。初期の気候表示で降水量・土壌・標高色・等高線を先読みしない。

既存の気候分類ID画像は約248KBでも、3,200×1,940画素のRGBA展開は約24.8MBになる。圧縮サイズだけでメモリを評価しない。ID抽出後は約6.2MBの8bit配列を保持し、不要な一時画像を解放する方針とする。土壌の1,600×970画素なら、ID配列は約1.55MB、RGBAは1枚約6.21MBである。GPUテクスチャ、MapLibre内部複製、既存等高線のメモリは別に計測する。

### 10.3 読込数・保持量・再試行

追加データは全国固定の許可リストで管理し、地域名や表示範囲をキーに資産を増殖させない。自然環境の任意データ取得は共通キューで最大2件とし、同じ資産の同時要求は1つのPromiseを共有する。取得中に切り替えた場合も、古い結果で現在の表示を上書きしない。

成功した全国資産は各1個を保持し、タブ往復やパン・ズームで再取得・再解析・再setDataしない。一時バッファは処理後に解放し、失敗したPromiseは再試行できる状態に戻す。4表示を各50回切り替えても、資産要求数と生存DOM数が増え続けないことを確認する。

通信タイムアウトは20秒を初期値とする。一時的な通信失敗の自動再試行は最大1回とし、その後は代替図と明示的な再試行操作を出す。404、分類不整合、壊れたデータを反復取得しない。

## 11. 代替表示・状態・実装接続

### 11.1 WebGLが使えない場合

代替画像の上にも都市名・地形名の操作要素を配置する。画像の実描画矩形と地理範囲を使い、余白を含む要素全体に機械的に座標を当てはめない。画像に焼き付いた名前と操作ラベルが二重に見える場合は、名前なしの代替画像を既存処理から小さく作り直す。

雨温図はSVGのまま表示し、気候面と土壌面の判定は同じIDデータを用いる。水資源の等降水量線の入／切、土壌の入／切、標高の淡い色にも代替画像で対応する。追加データの取得に失敗した時だけ、その追加表示が使えない旨を表示する。

代替図上の操作と、MapLibreでの描画・操作は別の検証結果として記録する。代替図の成功だけでWebGL動作済みとはしない。

### 11.2 状態とURL

既存の `climate / water / landform / contour` は維持し、表示名だけ「地形・土壌」へ変更する。追加する正規値は次とする。

## 12. 実装順序・作業保全・相談条件

### 12.1 将来の実装手順

1. 開始時のmain、既存資産ハッシュ、作業差分を確認し、実装用の作業枝を分ける。公開済みデータと詳細62ファイルを再生成しない。
2. 降水量・土壌それぞれの採用ファイル、分類、利用条件、容量を確認する。候補探索は各20分を目安に区切り、未確定なら何が足りないか記録する。
3. 新しい大容量データを必要としないR01・R02・R03・R06を実装し、狭い画面と代替表示の配置を確認する。
4. 保存DEMからR07の低解像度画像を作り、既存線との位置と色目盛りを確認する。
5. R04は年間格子1種類から基本2本を作る。R05は採用条件を満たした分布データだけを加工する。
6. 容量・要求数・メモリ・操作を測り、必要な範囲で簡略化する。各要件を実装済み／検証済み／転送済み／公開済みに分けて記録する。
7. 変更ファイルだけをGitHubへ反映し、CIと実際に確認できた画面を記録する。公開は、その時点の利用者の指示範囲を確認して扱う。

データ候補を確定できないことを理由に、同じ取得・加工を際限なく繰り返さない。進捗のない処理、同じ原因の失敗、予想より大きいデータが見つかった場合はその処理を止め、残る成果を保全する。長時間化した場合は完了済み要件と残作業を報告する。

### 12.2 転送方法と中断時の保全

現在の環境ではGitHubコネクターによるテキストファイル作成、Gitのtree・commit操作、ブランチ・PR作成が利用できる。通常の認証付きgit pushやバイナリの一括転送が利用可能かは、実装再開時に確認する。未確認の転送方法を前提に作業量を見積もらない。

少数のテキストはまとめたコミットで反映し、多数の変更がある場合は既存Blob SHAを使ったtree作成を検討する。既にGitHubにある資産は同じBlobを参照し、再送しない。新しいバイナリも、利用可能な方法を小さな代表ファイル1件で確認してから進める。ファイルごとの手動反復を増やすために分割しない。

中断時は未コミット差分と新規ファイルを復元可能な状態で保存し、基準commit、保存先、再開コマンドを記録する。転送台帳には「ローカルパス／リポジトリパス／サイズ／SHA-256／Git Blob SHA／転送状態／含まれるcommit」を持たせる。Blobだけ作成済みでブランチ未反映の状態も区別する。再開時はハッシュを照合し、完了済みの取得・加工・転送を繰り返さない。

### 12.3 裁量と相談の境界

| 実装側で判断してよいこと | 利用者へ確認すること |
|---|---|
| 追加候補の1,500・2,000mm線を省く | 基本の500・1,000mm線を省く、年降水量以外へ意味を変える |
| 原データの意味を保つ画像縮小・圧縮・線簡略化 | 記載期間を変更する、誤差や欠測を隠して境界を補う |
| ラベルをずらす、引出線を付ける、近接小型図を使う | 対象都市名を間引く、雨温図を地図下だけにする |
| 同じ分類のより小さい配信形式を選ぶ | 実分布を模式図へ置き換える、土壌機能を取り下げる |
| 既存ファイル・Blobを再利用し、変更分だけ送る | 大容量の再取得・再生成が不可避、容量上限を目的変更なしに満たせない |
| 原分類と教育用語の違いを正確に説明する | 米国本土以外へ対象を広げる、有料サービスを導入する |

一つの軽量化案で目的を保てる場合は、毎回承認を求めず判断を記録して進める。核心の操作や地理的意味を失う場合だけ、確認済みの代案・影響・残作業を示して相談する。

| A26 | 全体 | 気候初期表示で降水量・土壌・標高色・等高線を先読みしない |
| A27 | 全体 | 資産別容量、展開量、線座標数が第10章の上限内に収まる |
| A28 | 全体 | 同時取得は2件以内。同一要求を共有し、遅着結果・失敗後再試行を正しく扱う |
| A29 | 全体 | 4表示を各50回往復しても要求数・生存DOM数が増え続けず、一時バッファを保持しない |
| A30 | 全体 | WebGLと代替図で、都市・気候・地形・土壌の操作と表示範囲をそれぞれ確認する |
| A31 | 全体 | 390×844、820×1180、1180×820、1280×800で横はみ出し・主要操作の隠れがない |
| A32 | 全体 | 旧URL、追加状態、戻る／進む、農業・畜産・主要産業との選択とカメラ保持に回帰がない |
| A33 | 全体 | `dist`に詳細等高線・原DEM・原格子を含めず、保全済み資産を変更しない |
| A34 | 全体 | 影響する自動試験・ビルド・CIを通し、実測値と未確認端末を分けて記録する |

実測には、端末・ブラウザ・回線条件、初回と再表示の転送量、取得・展開・描画開始の時間、都市選択からカード表示までの時間、取得数、計測可能なメモリを添える。操作応答は読込済み状態で200ms以内を目標とするが、達成を実測前に断言しない。

WebGLを利用できるブラウザと実機Safariが用意できない場合は、その項目を「未確認」と記録する。代替表示の結果から補完しない。重い停止・強制再読込が出る場合は第12章の裁量内で縮小し、目的を保てない場合は公開へ進めず相談する。
