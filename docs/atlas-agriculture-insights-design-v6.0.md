## 0 引き継ぐ担当者が最初に読むこと

本改修は、作物・畜産の分布から地域間の関係を読み、自然条件や飼料・加工の仕組みを理解し、国内用途と貿易の規模で確かめられるようにする。ユーザーは以下の方針に同意し、まず設計書の作成を依頼した。実装を開始するのは、次の実装指示を受けてからである。

1. 地図の下に、複数の分布を結びつける短い解説を置く。選択すると関係する作物と畜産などを同じ地図で強調する。右側の全米統計は変えない。
2. 既存の5作物の詳説に、供給元と行き先を同じ尺度で示す横棒を追加する。輸入・在庫を含め、同じ年度・品目基準の数量で計算する。
3. 作物に必要な条件と、その地域が備える条件を対応する文字強調で示す。生育条件と、大規模生産に有利な条件を混同しない。

本書は既存の `docs/atlas-agriculture-livestock-design-v5.0.md` に対する追加設計である。地図全体の一覧性、作物と畜産のチェックボックス、全米販売収入の階層表示、既存の輸出先円グラフと世界生産シェアを引き継ぐ。変更のない要件はv5.0と現行コードを参照する。版番号は文書の版であり、既存の地理資産ディレクトリを一括変更する指示ではない。

現時点でユーザーの判断を必要とする未決事項はない。原資料の表番号・系列ID・取得ファイルと数値の確定、文章の裏づけの追加確認、画面寸法の調整は実装担当者が行う。根拠や操作性の制約で本書の完成形を満たせない場合のみ、代替案と影響を示して相談する。

## 3 画面構成

### 3.1 iPad横画面とPC

現在の二列構成を維持する。左列を「地図・表示切替 → 凡例 → 関係解説」、右列を「全米概説 → 販売収入 → 輸出入金額」とする。下部には現在どおり作物別・畜産別の詳説を置く。関係解説は `.atlas-map-column` の中で通常の文書フローに置き、右列の最下端の高さを測って埋める処理はしない。

地図を追加の文章に合わせて縮めない。初期表示で地図全体と分野切替を同時に見られることを優先し、関係解説全体を初期画面へ無理に詰め込まない。地図の下に自然に続き、右の統計を読む際にも左に解説が残る構成とする。

見出しは「分布のつながりを読む」を初期案とする。カードを大きな箱として装飾せず、3行の短い解説項目として積む。各項目は見出しと要点を常時表示し、本文は2〜3文を目安とする。iPad横では本文まで表示し、地図で比較する操作ボタンを各項目に置く。文章自体をすべてボタンにせず、コピーやリンク操作を妨げない。

### 3.2 iPhone縦画面と狭い画面

読む順番は「分野切替 → 地図 → 選択説明の退避先 → 凡例 → 関係解説3件の要点 → 全米概況 → 作物・畜産の詳説」とする。旧v5.0の『地図の次に概況』は、この短い関係解説の挿入について更新する。

関係解説は見出しと1文の要点を表示し、詳しい本文だけを開閉する。初期状態の3件合計をおおむね240 CSS px以内に収めることを目安とし、本文の縮小や固定高での切り落としはしない。重要な着眼点を開閉操作の奥に隠さない。操作部は44 CSS px以上のタップ領域を確保する。

レイアウトの切替は端末名ではなく利用可能な幅で決める。iPadの分割表示は一列へ移行できる。iPhone横画面では高さが限られるため、長い地図上カードを避け、短い表示と地図外の説明を用いる。文書全体の縦スクロールを基本にし、地図下の解説専用スクロール枠を作らない。

### 3.3 地図上の付箋と既存の地域説明

関係解説は複数対象の比較、既存カードは単一地域の説明という役割を持つ。地図上に表示するカードの容器は一つを共有する。関係を選ぶと既存の地域カードを閉じ、地域を直接タップすると関係の強調を解除して、その地域の説明へ移る。

カードには対象名、短い補足1〜2文、下の説明へのリンクを置く。地図の全域を説明文で覆わない。カードを置く候補は選択対象、畜産記号、地名、分野・層操作、拡大縮小ボタンを避ける。安全な位置がなければ、既存の `data-selection-slot` を使って地図の直下に表示する。選択対象を隠してまで地図上に置かない。

複数の対象が広く分布して安全領域を判定できない場合も地図外へ退避する。カードのための自動パン・自動ズームはしない。再配置では地図の再生成を行わず、回転・画面リサイズの後に座標を再評価する。

## 4 関係解説と根拠の扱い

### 4.1 初期に置く3件

以下は実装原稿の起点である。見出し・主旨は固定し、本文は出典照合のうえ読みやすく調整する。所在地の近接だけで経済効果の大きさや因果を計算したと説明しない。

**A とうもろこしと豚が近くに集まるのはなぜ**

要点案：豚の飼料となるとうもろこしと大豆粕が、耕種と畜産を結びつける。

説明では、中西部の作物地帯と養豚を関連づけ、飼料の調達と加工・出荷の仕組みを読む。USDA ERSは豚の肥育飼料としてとうもろこしと大豆粕を挙げる[S1]。近いほど必ず有利という定量断定や、飼料がすべて地元産という記述は避ける。ノースカロライナ等の立地を説明する場合は、生産体制や加工網を別の根拠で補う。

地図対象はcorn、soybean、corn-soybeanと、`iowa-hogs`、`east-cornbelt-hogs`。連続した作物の栽培域と、畜産の代表点という表示の違いを維持する。詳細先はとうもろこし・大豆の供給用途統計と養豚の基礎解説。

**B 小麦地帯と牛の分布はどうつながる**

要点案：同じ大平原でも、草地を使う飼育と穀物で体重を増やす肥育では土地との関わりが異なる。

説明では、牛の繁殖・育成・肥育という段階を区別する。グレートプレーンズの肥育集積を説明する公的資料[S2]を使い、「小麦の隣に牛がいるため、主な飼料が小麦である」とは書かない。現在の肉牛代表点だけで繁殖と肥育の内訳を示すことはできない。その内訳の新しい記号や領域を描く場合は、追加データの検証を先に行う。

地図対象はwheatと、`northern-plains-beef`、`southern-plains-beef`。草地の実データがない状態で草地ポリゴンを追加しない。詳説で飼料としてのとうもろこしにも接続する。

**C 雨の少ないカリフォルニアでなぜ稲作ができる**

要点案：稲作を支えるのは降水の多さだけでなく、必要な時期に田へ水を届けられる条件である。

説明では、稲の生育条件、平坦な土地、水を入れて排水する管理を結びつける。米国の稲作が灌漑を利用することとサクラメント渓谷が主要地域であることはUSDA資料[S3]に基づく。山地の雪・貯水・灌漑の具体的な経路は既存 `sacramento-rice` の出典を再確認する。河川が近いことだけを取水経路の証拠としない。

地図対象は既存のriceと、確認できる河川・地形。対象水系を一意に指定するIDがない場合、河川全体を特定の灌漑経路のように強調しない。初期版では稲作域と地名の強調だけでも成立する。詳説先は米の原稿と数量収支。

### 4.2 酪農の扱い

初期の一覧は3件に抑えるが、酪農の着眼点を捨てない。既存のカリフォルニア・アイダホ・上部中西部等の地域カードと下部の酪農解説で、気候、飼料と水、集乳・加工の条件を対応させる。山地や谷だけで全米酪農を説明しない。生乳を生産する場所と乳製品を加工する場所を区別する[S4]。

将来、4件目として「酪農が平原にも西部の谷にもあるのはなぜ」を追加できるデータ構造にする。初回から必須の切替や追加カード群を置く必要はない。

### 4.3 編集規則

各解説に観察、仕組み、適用範囲・例外、参照先を持たせる。画面ではこれを機械的な三段見出しにはせず、自然な文章として続ける。出典は文中の根拠に対応させ、地域や年度が違う資料を一つの観測結果へ混ぜない。

文章は事前に作成し、閲覧時にAI生成しない。`checkedAt` は実際の照合日とし、単にレコードを追加した日を査読日と呼ばない。2023年の作物図と2022年の畜産資料による概略比較であることは出典欄に示す。点の個数・距離・色面の面積から相関係数や生産量を算出しない。

## 5 地図の操作と状態

### 5.1 関係選択

強調は既存の地理座標と図形を使用する。作物の輪郭を少し強め、対象畜産記号を枠線等で目立たせる。河川・州境・地形陰影は残す。関係のない作物を消す方式は取らず、比較の文脈を維持する。記号サイズを頭数の大きさとして変えない。

既存作物データが作物ごとの広域MultiPolygonである場合は、その構造に合わせて強調する。局所的な塗り分けが必要だからと原稿選択用の長方形を新しい栽培境界として描かない。局所ハイライトには検証済みの構成図形IDを使い、IDがなければ広域の作物強調と地名・代表点で説明する。作物境界の細分化は追加調査として記録する。

作物・畜産が非表示なら、関係を選んでもチェックを勝手にオンへ戻さない。表示されている対象だけを強調し、「作物と畜産を表示して比較」のような明示的な操作を添える。その操作を押した時だけ必要な層をオンにする。本文は非表示設定にかかわらず読める。

### 5.2 状態遷移

| 操作 | 地図と説明 | 維持する状態 |
| --- | --- | --- |
| 関係を選ぶ | 関係IDを設定し、旧地域選択を解除。対象を複数強調 | カメラ、層チェック、全米統計、下部の作物タブ |
| 同じ関係を再選択または閉じる | 関係の強調と地図上補足を解除 | 位置・倍率、本文の開閉、統計 |
| 作物・畜産を地図から直接選ぶ | 関係の強調を解除し、既存地域カードを表示 | 既存の正規な状態管理 |
| 層のチェックを変更 | 当該層の強調も非表示。本文は残す | カメラと全米統計 |
| 詳説へのリンクを押す | 対象作物タブを開き、その節へ移動 | 地図カメラ、全米統計 |
| 他分野へ切替 | 農業の関係強調・カードを非表示 | カメラ、再訪用の有効な農業状態 |
| 地図をパン・ズーム | 同じ対象を強調し続け、カード位置を再計算 | 関係ID。画面外の対象へ自動復帰しない |

新しいURL項目は `relation=<id>` を推奨する。現行 `writeAtlasState` は旧 `insight` 等を削除するため、それを無確認で再利用しない。既存のcrop・region・animal・animalRegionは単一地域選択に使い、statsは下部作物タブの意味を維持する。

未知のrelationは無視し、正常な旧URLを維持する。関係と単一地域の選択が同時に指定された不正URLでは、有効な単一地域選択を優先してrelationを解除する。通常の関係選択では相互排他となる正規URLを出力する。関係を解除した時はrelationだけを除去する。

関係選択・層変更は履歴を追加し、カメラ移動は既存どおり履歴を置換する。戻る・進むで画面とチェックとURLが一致することを試験する。他分野が導入するURL項目を一括削除しない。状態関数をオブジェクト引数へ整理する場合も全呼び出し元との互換性を確認する。

## 6 供給元と行き先の統計

### 6.1 表示の目的と配置

作物別の「一般的な性質 → 米国の地域条件 → その地域に根づく理由」の文章に続けて、「作ったものはどこへ行くか」を置く。主な用途の文章は統計の説明として整理し、同じ用途説明を繰り返さない。その後に輸出先円グラフ、世界生産シェアと推移を置く。

各作物の供給と行き先は、同じ物量単位と同じ尺度の横棒2本で示す。両方の母数は総供給とし、国内利用だけを100%にするグラフへ暗黙に切り替えない。品目間では各品目内の構成比として比較し、同じ長さが同じトン数を意味するとはしない。

| 棒 | 表示する区分 |
| --- | --- |
| 供給元 | 国内生産、輸入、期首在庫 |
| 行き先 | 国内利用の排他的内訳、輸出、期末在庫 |

総供給量と対象年度を併記する。棒内の細い区分に文字を詰めず、外側に項目名と割合を常時表示する。小さな輸入を消したり視認性のために幅を水増ししたりしない。0%に丸まる正の割合は「1%未満」等で表し、数値表で元値を読めるようにする。

色は国内生産を主色、輸入と輸出をそれぞれ区別できる色、在庫を中立色とする。用途の色に地図の作物色という別の意味を持たせない。文字ラベルを必須とし、色だけで区分しない。実装はAstroでHTMLとSVGを出力し、閲覧時の統計APIや新しいグラフライブラリを追加しない。

### 6.2 収支の原則

基本の数量収支は次のとおりである。

期首在庫 ＋ 国内生産 ＋ 輸入 ＝ 国内利用 ＋ 輸出 ＋ 期末在庫

「生産量 − 輸出量」を国内消費としない。また、総供給は輸入と前年在庫を含むため、用途別の割合を「その年の国産収穫物が実際にたどった経路」と説明しない。輸出量／国内生産量を補助指標として使う場合も、国内産の輸出追跡率ではないことを明確にする。

原資料に統計調整・損失等の独立項目がある場合は、資料の符号と定義のまま別に管理する。ゼロへ切り捨てたり、食用や飼料に残差を押し込んだりしない。符号付き調整により非負の積み上げ棒で正確に表せない場合は、同じ尺度の供給棒と用途棒に調整差を別記し、無理に両棒を100%へ伸縮させない。画面上では短く示し、厳密な関係は数値表で確認できるようにする。

### 6.3 期間と出典の選び方

新しい数量収支は米国の同一販売年度でそろえる。初期候補は既存の世界生産統計と対応するMY2024である。最終採用は原資料の完備性を確認して決め、販売年度の開始日・終了日を各作物ごとに保存する。開始月を全作物で同じにしない。

一次候補はUSDA FAS PSDの米国の供給・分配系列[S6]。国内用途を細分化するため、USDA ERSのFeed Grains、Oil Crops、Wheat、Rice、Cottonの各データ表を調べる。これは系列選定方針であり、各表の最新ファイルと数値の取得完了を意味しない。原資料のダウンロードURL・表番号・列名・系列ID・単位・公表日を実装時の出典台帳で確定する。

各作物の収支は、可能な限り一つの公表版の整合した表から取る。PSDの総量とERSの用途内訳を混ぜる場合は、期間・品目基準・改定時点を照合し、合計が一致する場合だけ接続する。不一致なら用途を「国内利用」の一段で示し、細分の公表値を別の参考値として説明する。便宜的な比率配分で整合させない。

### 6.4 作物ごとの表示契約

| 作物 | 原材料の基準 | 国内利用の候補と注意 |
| --- | --- | --- |
| とうもろこし | 穀粒とうもろこし | 飼料等、エタノール向け、その他の食品・種子・工業用。原表の包含関係を確認して分割 |
| 大豆 | 丸大豆 | 搾油・加工、種子・その他。大豆粕と大豆油を丸大豆の用途へ重複加算しない |
| 小麦 | 未製粉の小麦 | 食用向け、種子、飼料等。製粉後の小麦粉の数量をそのまま加算しない |
| 綿花 | 綿繊維 lint | 国内紡績等。綿実・綿実油・衣料品を同一物量に混ぜない。調整項目に注意 |
| 米 | 精米換算で統一 | 食用等と飼料等は原表で分けられる場合のみ表示。もみ重量と混ぜない |

USDAの「feed and residual」は厳密な飼料消費量と同じではない。画面では「飼料等」と短く表示し、定義に統計上の残差を含むことを記す。調査上の残差を含む区分を、別に算出した収支差へ重ねて加算しない。

とうもろこしのエタノール用途が食品・種子・工業用合計の内数なら、内数と親合計を並列で足さない。エタノール製造後に飼料へ回る副産物は説明文でつなぎ、原料とうもろこしの棒の飼料区分へ再加算しない。大豆も加工によって粕と油が同時に得られるため、原材料の棒と加工後の用途説明を分ける。

換算は品目固有の公式係数に従い、使用係数と由来を保存する。共通のbushel換算をすべての作物に使わない。綿花を480ポンド俵のまま扱う場合は両方の棒で統一する。米の籾・玄米・精米の換算を根拠のない固定率で行わない。

### 6.5 輸入と輸出の説明

各作物に「輸入もあるのはなぜ」という短文枠を設け、原資料で確認できる品種・品質・用途・輸送・時期の違いを記す。米の香り米などは説明候補[S3]である。一般的な理由をその作物で実証済みの理由として流用しない。微量の輸入を主要特徴のように大きく扱わない。

輸入品の最終用途が統計から分からなければ、輸入の用途別割合は出さない。数量は確認できるが用途の内訳は確認できないことを短く示す。新しい輸入先円グラフや二国間フロー図は今回必須ではない。

既存の輸出先円グラフは2025暦年、収支図は販売年度となる可能性が高い。初期版では「輸出先の参考 2025暦年」と明示して別図として維持し、収支棒の輸出部分をそのまま分解した図のように線でつながない。同じ販売年度・品目範囲・総輸出量で相手国別データを再取得できた場合だけ、直接対応する内訳として扱う。

推奨IDは `corn-soy-hogs`、`plains-wheat-cattle`、`california-rice-water`。DOM上の出典先、作物タブ、畜産節が存在することをビルド前に検証する。新しい原稿には数値や地図座標を本文から抜き出す正規表現処理を使わない。

### 7.2 供給用途データ

新規 `src/data/atlas/supply-use.ts` に型と出典、`supply-use-generated.ts` に検証済み値を置く構成を推奨する。生データは配信しない。

| フィールド群 | 必須情報 |
| --- | --- |
| 識別 | cropId、countryCode、commodityBasis、unit、marketingYear、periodStart、periodEnd |
| 供給 | beginningStocks、production、imports |
| 行き先 | domesticUsesの各id・ラベル・値・定義、exports、endingStocks |
| 調整 | 原表のadjustments、符号規則、reconciliationの差と許容誤差 |
| 出典 | URL、表番号、系列ID、公表日、取得日、原ファイルSHA-256、加工スクリプト版 |
| 品質 | actual／estimate／forecast、complete／partial／unavailable、欠測理由 |
| 解説 | 国内用途の要約、輸入の理由、加工副産物の説明と各出典 |

元単位の値と表示換算値を区別する。割合は丸め前の値から計算し、表示直前に丸める。計算に使う数値列へ「約」等の文字を入れない。欠測はnullとし、ゼロで代用しない。

### 7.3 データ品質の処理

検算は同一キーでの行の一意性、単位・期間・改定版の一致、国内利用内訳と親合計の一致、供給と分配の一致、非負が必要な値の範囲を確認する。公表値の丸めがある場合、各項目の最小表示単位の半分を足し合わせた上限等、元表の精度から許容誤差を定義する。任意に1%の誤差を許す方法は使わない。

sourceに存在するsigned adjustmentと、単なる丸め誤差を分離する。後者はメタデータと数値表で示し、恣意的に一つの用途へ配賦しない。母数が0または負なら割合グラフを生成せず、理由を表示する。

完全な用途細分が得られなくても、整合した総収支が得られれば「国内利用」を一括で表示し、確認済みの用途を文章で説明できる。総収支そのものがそろわない作物は、欠測理由付きの数値表を残す。5作物の必須範囲を満たしたと報告せず、公開前に制約として知らせる。予測値しか得られない場合も無表示で実績に混ぜない。

更新時には手作業で生成済みTSの数値だけを書き換えず、原資料とスクリプトから再生成する。原ファイルが大きい場合は取得方法・公表版・ハッシュを残し、小さい必要列の抽出と出典台帳を保存する。GitHub Pagesの通常ビルドは既存の検証済み抽出を使い、毎回USDAへ問い合わせない。

## 8 文字強調と原稿の構造

### 8.1 編集方針

一段落に2〜3組を目安に、条件と地域の対応箇所を同じ種類の下線で強調する。重要語をすべて太字にしない。色が見えなくても文の順番と語句から対応が分かる文章にする。リンクの下線と区別するため、本文の対応強調は淡い下線または背景帯、リンクは従来のリンク色と装飾を用いる。

例として、とうもろこしでは「暖かい生育期」と「夏の温度」、「十分な水分」と「生育期の降水」をそれぞれ対応させる。「まとまった平坦な耕地」は大型機械を使う栽培に有利という次の文へ置き、生物学的な生育要件と混ぜない。音声入力にあった『高地』は現行原稿の『耕地』として扱う。

強調の種類は温度、水、土地・経営条件の3つを初期案とする。色は本文内の役割で固定し、地図の作物色とは別に管理する。細かい数値や出典には強調を広げない。下線の強調をタップ必須の操作にはしない。

### 8.2 実装するデータ形式

文章は文字列にHTMLタグを埋め込む方式から、段落とrunの配列へ段階的に対応する。runはtext、emphasisKind、pairIdを持てる。pairIdで必要条件と地域条件の対応を明示し、色だけに依存しない編集検査を可能にする。

既存の文字列段落はそのまま表示できるようにし、自然環境等の無関係な原稿へ移行を強制しない。描画はAstroの通常の文字列エスケープを使い、ユーザー入力や原稿に `set:html` を適用しない。強調付き文からプレーンテキストを得られるようにし、検索・読み上げ・非JavaScript表示を保つ。

pairIdを設定した場合は同じ段落または連続する文に対応する語句があることを確認する。すべての文へペアを強制せず、例外や不適合を説明する文は通常の表現を許す。

## 10 代替表示とアクセシビリティ

解説と数量図・数値表は静的HTMLで出力する。WebGL失敗時は現行の代替図を維持し、関係解説と対象地域名を読めるようにする。正しい座標変換を使って代替図の強調を実装できる場合のみ付加する。装飾的なピクセル領域を新しい地理境界へ流用しない。

代替図で比較ハイライトが使えない場合、「地図で比較」を無反応のまま残さず、対象地域の説明へ移る操作に替える。JavaScript無効時は関係本文と5作物の説明・図を順に読めるようにする。閉じたタブに内容が永久に隠れないことを確認する。

新規ボタンはキーボードで到達でき、EnterまたはSpaceで操作できる。選択状態をaria-pressed等で知らせ、開閉はaria-expandedと実表示を一致させる。閉じる際は可能な限り元の操作へフォーカスを戻す。読み上げ通知に長文の全再読込を使わない。

本文14〜16 CSS px、補助ラベル12 CSS px程度を初期値とする。収まりのために現行の小さなグラフ文字へさらに縮小しない。通常文字のコントラストは4.5対1、重要な図形・フォーカス表示は3対1を基準に確認する。200%拡大時は通常フローへ退避し、地図上カードの切り落としを避ける。動きを加える場合はreduced-motionに従う。

CSS pxでiPad相当1024×768と768×1024、1180×820と820×1180、iPhone相当390×844と844×390、狭幅375×667、PC1440×900を確認する。安全領域、ブラウザ表示領域の変化も考慮する。

各主要寸法で、初期表示、関係選択、単一地域選択、作物・畜産のオンオフ、供給用途図、長い本文、地図外退避を確認する。少なくともiPad横とiPhone縦で各関係を一度ずつ確認する。1枚の初期スクリーンショットだけで合格としない。

地図と分野切替の初期収まり、説明が意図した対象に対応すること、河川・州境・栽培域の重なり、グラフのラベル、ページ横幅を確認し、不具合は修正後に撮り直す。数値表と図の数字も照合する。

ブラウザの端末エミュレーション、WebGL有効なブラウザ、WebGL失敗時の代替図、実機Safariの確認は区別して報告する。GPU表示が確認できない環境で代替図だけを見て、地図ハイライトの実動作も合格としない。実機確認はユーザーが行う操作感の確認と分け、担当者が確認した範囲を記録する。

## 12 実装順序と公開手順

実装指示を受けた担当者は、以下の順序で進める。

1. 最新main、開いているPR、AGENTS.mdの有無、共通ファイルの変更状況を確認する。独立したブランチで作業し、自然環境の改修を古いコードで上書きしない。
2. 原資料を取得し、5作物の年度・単位・用途区分を確定する。数量収支の検算と3解説の出典照合を先に終える。細分が不可能なら第7章の代替表示を採用する。
3. 原稿・型・生成済みデータを追加する。地域ID、出典ID、詳細リンク、期間と合計を検証する。
4. 静的な関係欄、数量図、強調文を配置し、iPad横とiPhone縦で密度を確認する。右の統計と地図の寸法を不用意に変えない。
5. 地図の関係選択、URL状態、カードの共有・退避、チェックとの連動を実装する。既存地図を再生成しない。
6. 既存 `npm run check` と必要な追加試験、ブラウザの縦横画面検証を行い、出典・加工・QA文書を更新する。
7. 現行mainとの差分を再確認する。共通ファイルに後続変更があれば統合して、影響する状態・画面を再確認する。
8. 公開を含む実装指示を受けている場合、既存PR・mainへの反映手順を使い、GitHub Pagesのビルドと公開を確認する。公開URLと `_release.json` の版を照合し、完成画面と制約を報告する。

基準コミットの実際の公開ワークフローは `.github/workflows/pages.yml` であり、mainへのpushで試験、ビルド、静的完成サイト試験、release検証、GitHub Pagesへのデプロイを行う。手元の古い `publish-runbook.md` に『初期は検証のみ』とある部分を、現在も公開不能である根拠にしない。ワークフローの改変やホスティング移行は今回不要である。

今回の設計書作成ではソース変更・PR作成・mainへの反映・公開は行っていない。文書内の受入条件は次工程の合格基準であり、機能試験の完了記録ではない。
