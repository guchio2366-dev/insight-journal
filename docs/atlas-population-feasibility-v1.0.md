# 人口タブ：実装前の実現性調査と設計補足 v1.0

調査日：2026年9月14日  
対象：Insight Journal／北米アトラス／人口タブ  
前提：承認済み「atlas-population-design-v1.0.md」の画面構成と初版範囲を維持する。今回の成果物は調査と設計補足であり、実装を開始する指示ではない。

## 1. 結論

**現在の構想を維持して、実装前の準備を進める方針を推奨する。** 地図を共用し、選んだ分野・都市圏だけを読み込む構成には、負荷を抑える合理的な見通しがある。ただし、人口データを加工した後の容量と実機での動作は未測定であり、「軽く動くことを確認済み」とは判断しない。

時間の不確実性が大きいのは、画面を増やす作業より、**原資料の取得・集計・地域コードの照合**である。今回、公式の配布先と具体的なファイルを特定した。一方、宗教の州別集計の取得・再利用方法、投票データと郡境界の対応、都市圏の加工後容量が残る。

利用者に新しい画面構成の判断を求める必要は、現時点ではない。残項目はまず技術・資料の確認で解消する。資料の利用許可や有料契約が必要になった場合、または承認済みの4分野・3都市圏を変える必要が生じた場合に、具体案と影響を示して相談する。

### 3.1 Census：公式一括配布を第一候補にする

Censusは数値のAPI問い合わせにキーを必須としている。メタデータの問い合わせはキーなしでも利用できる。この違いを設計へ反映する。[Censusの2026年6月公式案内](https://content.govdelivery.com/accounts/USCENSUS/bulletins/41aaf23)

まず、キーを用いた個別問い合わせに依存しない公式のTable-Based Summary Fileを取得候補にする。表ごとに推計値と誤差情報をまとめて取得し、必要な地理レベルと列を事前抽出する。全表一式を取得する必要はない。APIを併用する場合も更新作業のための取得経路とし、閲覧者のブラウザからCensusへ問い合わせる構成にはしない。

| 用途 | 確認したファイル | 提供元一覧の容量表示 |
|---|---|---:|
| 総人口 | `acsdt5y2024-b01003.dat` | 17M |
| 人種・民族 | `acsdt5y2024-b03002.dat` | 79M |
| 地域名の対応 | `Geos20245YR.txt` | 87M |
| 項目ラベル | `ACS20245YR_Table_Shells.txt` | 5.4M |

表の所在：[5YRData](https://www2.census.gov/programs-surveys/acs/summary_file/2024/table-based-SF/data/5YRData/)。ラベルの所在：[documentation](https://www2.census.gov/programs-surveys/acs/summary_file/2024/table-based-SF/documentation/)。容量は配布一覧の丸め表示であり、ダウンロード実測値ではない。

これらは多くの地域を含む**作成者側の原資料**である。サイトに置くのは必要な郡・地区・全国値へ加工した結果であり、閲覧時にこの容量を転送する設計ではない。元ファイルの取得・加工を通常のサイトビルドから分離すれば、毎回の修正で再取得を待つ必要もなくなる。

民族の大分類は承認済みの8分類を維持する。ヒスパニック系を1分類とし、それ以外の7分類は非ヒスパニック系に限定する。詳細な出自・国籍・出生地を混ぜて分類数を増やさない。原表の列番号は取得方式により表記が異なるため、API名と一括配布名の対応をラベル資料で照合する。

### 3.2 宗教：公表集計を使う取得経路の確定が必要

Pewの一般公開個票には地理情報がなく、そこから州別割合を再集計することはできない。地域情報を含む制限付き個票は別の利用経路である。今回の目的には、閲覧可能な州別の公表集計を使う方針が適している。[個票の説明](https://www.pewresearch.org/dataset/2023-24-religious-landscape-study-rls-dataset/)、[州別公表例：カリフォルニア](https://www.pewresearch.org/religious-landscape-study/state/california/)

ただし、予定する州別集計の一括取得・再掲載まで確認済みとは扱わない。Pewの条件には出典・著作権表示、翻訳時の注記があり、無許可の自動収集や主要部分の再掲載に制約がある。公式の集計ダウンロードや許容される利用範囲を確認し、必要なら許可取得の具体案を用意する。今回、アカウント作成・申請・問い合わせ送信・州ページの一括収集は行っていない。[Pewの利用条件](https://www.pewresearch.org/about/terms-and-conditions/)

翻訳したPewの内容には、条件に定める次の注記を付ける。

> Pew Research Center has published the original content in English but has not reviewed or approved this translation.

集計値の扱いも取得前に固定する。プロテスタントなどの上位分類は、公表された上位集計がある場合はそれを使用する。丸めた下位分類の合計は上位値と一致するとは限らない。`<1%`を0%へ置換せず、上位値がない合算を正確な単一点として捏造しない。区間しか求められず凡例の境界をまたぐ場合は、区間表示または判定不能として扱う。全国値は公表された全国集計を使用し、州別割合の単純平均や総人口による加重で代用しない。

### 3.3 投票：最新の配布版を固定し、2024年だけを抽出する

確認時のデータセットは「County Presidential Election Returns 2000–2024」version 20.0、公開日は2026年2月25日。CC0 1.0の指定がある。`countypres_2000-2024.tab`は9,845,506 bytes、元CSVは10,222,208 bytesと登録されている。これは2000–2024年全体の原資料サイズであり、2024年分の配信用サイズではない。[公式メタデータ](https://dataverse.harvard.edu/api/datasets/:persistentId/?persistentId=doi:10.7910/DVN/VOQCHQ)

表示は承認済みの「投票傾向」を維持する。共和党と民主党の得票率差を5段階で示し、分母はその他候補も含む全有効票とする。現在の支持政党調査、予測、個人の政治的傾向へ読み替えない。

地域コードの欠落、候補者の複数政党表記、投票方式別と合計行の重複を確認する。特にコネティカット州の旧郡と新しい統計地域のように境界が合わない場合、名称や面積比だけで票を割り振らない。公式に対応を取れる元集計を探し、必要なら投票だけの例外境界を持つ設計へ進める。その場合は容量と「郡境界を共用する」前提を再評価する。

## 4. 都市圏1件の検証仕様

**最初の対象はニューヨーク都市圏とする。** 複数州にまたがる人口集中と小さな地区の表示を確認でき、中心部と周辺を見比べる目的に合うためである。全候補を実測して最も重いと判定したわけではない。

### 対象地域と意味

都市圏は2024年ACSが採用する2023年7月のOMB区分に合わせ、対応する都市圏コードと所属郡一覧から対象を確定する。地図上の長方形や独自の通勤圏で切り取らない。ACSの地区は2020年基準を起点とし、その後の変更を含む2024年の配布境界との対応を確認する。都市的地域の輪郭は2020年Urban Area、主要市の輪郭は採用時点を明記して別に表示する。[ACSの地理時点](https://www.census.gov/programs-surveys/acs/geography-acs/geography-boundaries-by-year.html)

「郊外」の解釈は、承認済みの**主要市の外側にある都市的地域を読むための目安**を維持する。都市圏内で主要市以外の土地を、すべて郊外と断定しない。地区を輪郭で切り分けて人口を面積按分せず、密度の分子・分母は元の地区単位で保持する。

全国の中心・周辺の説明に使うNCHSは、郡単位の別の分類である。2023年版は計3,144の郡相当地域を分類し、コネティカットのplanning regionsを含む。全国の人口構成比はその分類コードに採用ACSの人口を結んで計算し、NCHS掲載の2022年人口割合を転記しない。[NCHSの分類・配布入口](https://www.cdc.gov/nchs/data-analysis-tools/urban-rural.html)

### 確認した境界ファイル

| 原資料 | 一覧の容量表示 | 検証での使い方 |
|---|---:|---|
| `cb_2024_36_tract_500k.zip`：ニューヨーク州の地区 | 1.8M | 都市圏に属する地区を抽出する候補 |
| `cb_2024_34_tract_500k.zip`：ニュージャージー州の地区 | 764K | 州をまたぐ結合と細かな地区の表示を確認 |
| `cb_2024_us_county_5m.zip`：全国郡 | 2.8M | 全国の主題図の境界候補 |

いずれも[2024年版の公式配布一覧](https://www2.census.gov/geo/tiger/GENZ2024/shp/)で存在と容量表示を確認した。州全体のZIPには形状以外のファイルも含まれ、GeoJSONへ変換すると容量が増える場合もある。**この表から都市圏の配信量が1MB以下になると推定してはいけない。** 必要州の最終集合は、都市圏の所属郡一覧で確定する。

CensusのCartographic Boundary Filesは主題図向けに簡略化された境界である。まずこの形式を評価し、小さな地区が消える・水際が不適切になるなどの問題があれば、より詳細な境界を元に簡略化し直す。人口密度の面積は表示ポリゴンから再計算せず、対応する公式の陸地面積を使用する。[境界ファイルの説明](https://www.census.gov/geographies/mapping-files/time-series/geo/cartographic-boundary.html)

### 将来の検証で記録する項目

| 項目 | 記録・判定方法 | 判断に使う理由 |
|---|---|---|
| 統計と形状の対応 | 対象地区数、IDの重複・不一致・除外理由 | 軽くても地域が欠けている地図は採用できない |
| 加工後容量 | 未圧縮bytes、配信に使う圧縮方式のbytes | 原資料のZIP容量では閲覧時の転送量を判断できない |
| 形状の複雑さ | 地区数、頂点数、無効形状、簡略化前後の差 | 同じファイル容量でも描画・選択処理の負荷は異なる |
| 見た目 | 最大倍率10を含む中心部・周辺部・水際の比較 | 軽量化で地区を見分ける目的を失っていないか |
| 集計 | 総人口、欠測、正しい陸地面積での密度 | 形状の軽量化が統計の値を変えていないか |
| 作業時間 | 取得、結合、簡略化、検算を別々に記録 | 残り2都市圏の工数を根拠付きで見積もるため |

今回、この変換処理や検証用の画面は作成していない。上表を、次にデータ検証が許可された際の作業仕様とする。

## 5. サイトを重くしないための設計補足

レイアウトと導線は承認済みのままにする。軽量化は主にデータの持ち方と取得時期で行う。

| 設計 | ユーザー体験への効果 |
|---|---|
| 既存の地図インスタンスを共用 | タブごとに重い地図を増やさない |
| 人口タブを開いてから人口用の形状・数値を取得 | 他分野の閲覧で人口データの通信待ちを増やさない |
| 人口・民族・投票の郡形状を、地域が一致する範囲で共用 | サブタブ切替で同じ境界を重複取得しない |
| 宗教は州の形状と小さな数値表を選択時に取得 | 地区レベルのデータを宗教表示に持ち込まない |
| 都市圏は選択した1件を取得、キャッシュは最大2件 | 3都市圏を最初から待つ必要がなく、往復も扱える |
| 使わない都市圏は描画元と保持参照を整理 | 非表示にするだけでメモリを保持し続けることを避ける |
| 原資料は事前加工し、検証済みの静的ファイルを配信 | 閲覧速度を外部統計サービスへの問い合わせに依存させない |

不要属性の除去、形状の簡略化、データの分割はMapLibreの公式ガイドにもある方法である。適用するだけで速度を保証できるわけではなく、実データでの比較が必要になる。[MapLibreの大規模GeoJSONガイド](https://maplibre.org/maplibre-gl-js/docs/guides/large-data/)

今回参照した既存コードでは、地図は1個、worker数は1、描画倍率は端末倍率の上限2である。一方、共通の初期読み込みには既存分野のデータがあり、自然環境の取得済みデータには保持用キャッシュがある。人口用データを共通の初期読み込みへそのまま追加せず、他タブとの往復後の保持状態も確認対象にする。[参照した地図制御コード](https://github.com/guchio2366-dev/insight-journal/blob/e9597ce4644f3d8d64601f989d1e584fac142a07/src/scripts/atlas-explorer.ts)、[自然環境データの取得処理](https://github.com/guchio2366-dev/insight-journal/blob/e9597ce4644f3d8d64601f989d1e584fac142a07/src/lib/atlas-nature-data.ts)

### 容量と動作の判定基準

以下は**実測結果ではなく設計目標**。KBは1,000 bytes、MBは1,000,000 bytesとする。提供元一覧のM/K表記とは区別する。

| 対象 | 初期目標 | 測定時の条件 |
|---|---|---|
| 人口を開く前 | 人口専用データの追加通信0件 | 初回の他タブ表示で通信一覧を比較 |
| 人口の追加制御コード＋初期数値 | 圧縮後150KB以内 | 新しい地図形状は別に計上 |
| 全国郡の形状 | 圧縮後1MB以内 | 採用する地理範囲を固定して測定 |
| 都市圏の詳細形状 | 1都市圏あたり圧縮後1MB以内 | 主要市・都市的地域の輪郭を含めて計上 |
| 人口タブ初回／都市圏初回表示 | 操作から主要図の表示まで2秒以内を暫定目標 | 下り10Mbps・遅延100msの一定条件、初回を5回測り中央値と最大値を記録 |
| 読み込み済みの分類切替 | 操作から図の更新まで200ms以内を暫定目標 | 同じ端末で複数回測定。カードだけの反応時間で代用しない |
| 都市圏の往復 | 保持は最大2件、往復で際限なく増加しない | NY→LA→DFW→全国を10回。画面停止・再読み込み・保持状態を記録 |

転送量、展開後のオブジェクト量、地図内部の処理、GPUの負荷は別々である。1MB以下でも操作が重ければ不合格とする。既存の自然環境タブを使った後も確認し、画面幅の再現と実機iPad/Safariの確認を区別する。実機確認の手段がない場合は未確認と明記する。

容量を超えた場合は、不要属性を除く→共有する境界を保つ形で簡略化→必要地域に分割、の順で調整する。それでも難しい場合に静的ベクトルタイル等を評価する。最初から新しい地図基盤や有料サービスを導入する前提にはしない。

## 6. 時間が膨らまない進め方

最初から4分野の画面を同時に仕上げるより、次の順で不確実性を減らす。これは今後の作業設計であり、今回実装へ進むものではない。

| 順序 | 作業 | その段階を終えるために必要な結果 |
|---|---|---|
| A：取得の成立 | ACSの小標本、Pewの集計取得・再利用経路、MITの2024年抽出を確認 | 「何を取得すれば作れるか」が具体的に決まる |
| B：NYだけのデータ検証 | 数値・形状を照合し、配信用にした際の容量を測る | 都市圏1件の容量と加工時間が分かる |
| C：見積もりの更新 | A・Bの結果から残作業を再計算 | 取得待ちと作業時間を分けた見積もりになる |
| D：実装 | 別途、実装開始の指示を受けて着手 | 承認済みの4分野・3都市圏を順に完成させる |

A・Bは検証の順番であり、初版を人口分布だけに縮める提案ではない。画面枠・カード・凡例・郡の地図は共用できるため、タブが4つになることがそのまま開発量や閲覧負荷の4倍を意味するわけではない。

現時点で「あと何時間で完成」とは確約しない。特に外部の許可・登録が必要になる場合、その待ち時間を実作業の時間と混ぜない。同一の取得方法で失敗が続けば、原因を記録して公式の別形式を一度確認し、無制限に待たず他の確認へ進む。NYが処理できれば、その実績を残りの都市圏の見積もりに使う。
